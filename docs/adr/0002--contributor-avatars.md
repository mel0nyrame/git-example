# 保留贡献者名单并生成独立头像

状态：implemented

## 问题

课程需要展示所有已有贡献者，并及时展示新学员。
聚合图片服务的缓存会延迟整个名单的更新。
[GitHub 贡献者 API](https://docs.github.com/en/rest/repos/repos#list-repository-contributors)也有缓存，且账号识别依赖提交邮箱。
只按成员目录生成名单，会遗漏没有个人目录的贡献者。

## 决策

将 GitHub 贡献者、课程成员和已收录账号取并集。
使用 `.github/contributors.json` 保存持久名单。
使用账号 ID 去重，避免账号更名造成重复。
自动更新只补充或更新账号，不根据统计结果或目录删除账号。
该保留策略防止缓存和目录变化移除已有贡献者。
README 是名单的生成物，不作为名单来源。

仅原仓库 `main` 上的独立任务有内容写权限。
任务使用平台临时令牌，只提交名单和 README。
任务不在 PR 上运行，不改变学生 PR 的权限例外。
[PR 文件权限决策](0001--pr-file-permissions.md)继续有效。

## 备选方案

- 使用聚合图片服务。整张图片的缓存会阻碍新成员展示。
- 只使用贡献者 API。上游缓存和邮箱归属仍会遗漏新学员。
- 只读取成员目录。没有成员目录的贡献者会丢失。
- 从 README 头像反推名单。生成物会变成隐含的数据来源。

## 后果与风险

持久名单保证已收录账号不会因上游统计变化而消失。
成员目录使新学员无需等待贡献者统计更新。
贡献者 API 必须读取全部分页，不能只读取第一页。
账号查询失败时停止更新，避免提交缺人的列表。
账号删除或需要移除名单时，由维护者明确处理。
GitHub 头像缓存仍会延迟个人头像图片的变化。

机器人提交需要仓库允许工作流写入默认分支。
推送冲突时任务失败，由后续任务或维护者重跑恢复。
按[令牌事件规则](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/trigger-a-workflow)，`GITHUB_TOKEN` 推送不会递归触发普通 `push` 工作流。
操作入口和验证命令由[维护说明](../contributors.md)负责。
